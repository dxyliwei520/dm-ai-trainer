# H3 LoRA 训练 · 踩坑记录

> 2026-11-09 一天内踩到并修掉的坑，按重要性排序。
> 每条都含：**现象 → 根因 → 修法 → 判据**

---

## 1. 切段会「把旧视频重切一遍」（最坑）

**现象**：上传第 2 个视频点「切段」，结果片段里出现的是第 1 个（旧）视频的内容。

**根因**：脚本每次都遍历 `raw\` 里**所有**视频，且输出固定从 `01.mp4` 起编号 →
旧素材重新切一遍，覆盖了同名文件。

**修法**（三层）：
1. 输出改成**按来源命名**：`<源文件名>_001.mp4`，不同素材永不冲突
2. 新增 `--only <文件名>`：只切指定素材
3. 写 `videos\_cut_manifest.json` 记录「哪些素材已切过几段」，
   全局「切段」只处理**未切过**的

**判据**：
```
[skip] already cut (2): videoA.mp4, videoB.mp4
[info] nothing to do - every source is already cut
```

## 2. 连点「开始训练」起两个训练进程

**现象**：GPU 抢资源、缓存跑两份、日志交错。

**根因**：`/api/train` 里 `if STATE["running"]` 与随后置位之间有竞态 →
两次快速请求都能通过；且训练进程被外部杀掉后 STATE 归零（按钮解锁），
但真正的 python 子进程还活着 → 刷新页面又能点一次。

**修法**（三道防线）：
1. `with LOCK:` 包住「检查 + 立即置位」
2. 启动前 `_kill_strays()` 清理残留的 `minimax_h3_*` 进程
3. 前端 **常驻轮询**（`setInterval(poll, 2000)`），刷新页面也能看到真实状态

**判据**：第二次请求返回 `{"detail":"已有训练在跑"}`，进程数仍是一组。

## 3. 卡在 `Loading MiniMax-H3 Qwen3-VL processor`（GPU 0%、CPU 0%）

**现象**：训练看起来启动了，但 GPU 占用 0%、CPU 不增长、日志停在加载 processor，
可以停好几分钟甚至更久。

**根因**：musubi 代码**写死**从 HuggingFace 仓库加载配置：

```python
Qwen3VLProcessor.from_pretrained("MiniMaxAI/MiniMax-H3", subfolder="processor")
Qwen3VLConfig.from_pretrained("MiniMaxAI/MiniMax-H3", subfolder="text_encoder")
```

国内访问 HF 慢/被卡时，这个 HEAD 请求会**无限等待**（没有超时兜底）。

**修法**：
1. 把 7 个小配置文件拷到本地（共 ~11 MB）：
   `E:\ai-train\models\h3_configs\{processor,text_encoder}\`
2. 给 `env-musubi\Lib\site-packages\musubi_tuner\minimax_h3\text_encoder.py` 打补丁，
   支持环境变量优先本地：
   ```python
   local_dir = os.getenv("H3_PROCESSOR_DIR")
   if local_dir and Path(local_dir).is_dir():
       return Qwen3VLProcessor.from_pretrained(local_dir)
   ```
3. 网页训练自动设 `H3_PROCESSOR_DIR` / `H3_TEXT_ENCODER_CONFIG_DIR`
4. 另加 `HF_HUB_ETAG_TIMEOUT=10` / `HF_HUB_DOWNLOAD_TIMEOUT=30` 作为兜底

**注意**：`HF_HUB_OFFLINE=1` **不能**直接用 —— 缓存里缺项时会直接报错
（`couldn't find them in the cached files`），所以要走「本地目录」而不是「离线模式」。

**判据**：13 段素材的 cache_text **67 秒跑完**，日志有 `Saving ... text cache` 逐条推进。

## 4. 56 帧训练比 22 帧慢 60 倍

**实测**（RTX 5070 Ti 16GB，448×256，块换出 28）：

| 帧数 | 每步 | 1000 步 |
|---|---|---|
| 22 | **4 秒** | **67 分钟** |
| 56 | **253 秒** | **70 小时** |

**根因**：帧数 ↑ → 序列长度 ↑ → 注意力显存爆掉 → 块换出疯狂搬运，
GPU 功耗从 200W 掉到 66W（在等数据，不是在算）。

**判据**：GPU 功耗是最好指标 —— **>150W 才是在真算**；66W 就是在搬数据。

**结论**：训练一律 22 帧（0.92 秒/段）。长片段只在推理时用。

## 5. PowerShell 传 JSON 给 curl 会被吞引号

**现象**：`curl -d '{"a":1}'` → 服务端 500 或 `JSONDecodeError`。

**修法**：**写文件再 `--data-binary @file`**

```powershell
[System.IO.File]::WriteAllText("$env:TEMP\b.json", '{"a":1}', (New-Object System.Text.UTF8Encoding($false)))
curl.exe -X POST -H 'Content-Type: application/json' --data-binary "@$env:TEMP\b.json" http://...
```

**判据**：服务端能正确解析（不再是 `Expecting property name enclosed in double quotes`）。

## 6. `.bat` 里不能写中文

**现象**：双击 bat 立刻报一堆 `'l' 不是内部或外部命令`、`文件名语法不正确`。

**根因**：cmd 按 ANSI 解析 bat，中文注释/提示会被拆坏。
（即使文件是 UTF-8 + `chcp 65001` 也一样，因为 chcp 在解析之后才生效）

**修法**：**bat 一律纯 ASCII**（注释也用英文）。

**判据**：
```powershell
([System.IO.File]::ReadAllBytes($bat) | Where-Object { $_ -gt 127 }).Count   # 必须为 0
```

## 7. 含中文的 `.ps1` 必须带 UTF-8 BOM

**现象**：脚本内容明明正确，却报 `Missing closing '}' in statement block`。

**根因**：PowerShell 5.1 读**无 BOM** 的 .ps1 时按 GBK 解码，中文变乱码把结构撑坏。

**修法**：
```powershell
[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($true)))  # $true = 带 BOM
```

**判据**：文件头三字节是 `EF BB BF`。

## 8. PowerShell 变量名大小写不敏感

**现象**：脚本里 `$m`（python 路径）和 `$M`（模型目录）写在一起，
结果 python 路径变成了模型目录 → `'F:\...\models' is not recognized`（9009）。

**修法**：变量名要有区分度：`$pyExe` / `$modelsDir` / `$cfgDir`。

## 9. `Start-Process` 对 venv 里的 python.exe 偶发 "Access is denied"

**现象**：`Start-Process -FilePath E:\ai-train\env-musubi\Scripts\python.exe ...` 直接报拒绝访问。

**修法**：用 `cmd /c "<bat 里写完整命令> > log 2>&1"`，把命令写进 .bat 再执行。

## 10. 缩放不能默认居中裁切

**现象**：竖屏素材被裁掉大半，重要内容丢失。

**修法**：三种模式可选，**默认「模糊填充」**（等比缩放 + 背景高斯模糊填充）：
- `blur`（默认）：不裁切，无黑边
- `pad`：不裁切，有黑边
- `crop`：填满但会裁掉边缘

**判据**：竖屏素材处理后，画面完整且没有黑边。

## 11. musubi 缓存文件名带帧数

**现象**：改了 `target_frames` 后训练报 `No training items found in the dataset`。

**根因**：缓存文件名含帧数（`01_00000-022_...`），改帧数后旧缓存对不上。

**修法**：改帧数/分辨率 → 重跑切段或训练（网页会自动重新缓存）。

## 12. 训练期间必须停 ComfyUI 8189

**现象**：训练启动后报 OOM 或极端变慢。

**根因**：ComfyUI 常驻约 4.6 GB 显存，加上 33B 模型训练必然不够。

**修法**：网页勾「停 ComfyUI」（默认勾选），训练前自动 `schtasks /End /TN ComfyUI-D-8189`，
跑完自动 `schtasks /Run` 恢复。

⚠️ 注意 `ComfyUI-D-8189` 是**看门狗循环**，用 taskkill 杀掉 python 后 15 秒会自己重启，
所以必须用 `schtasks /End` 停任务，而不是只杀进程。

## 13. 模型选择必须按底座匹配

**现象**：训好的 LoRA 加载后画面怪但没报错。

**根因**：三个 H3 底座互不通用：
- `fl2va_pruned`（官方基础，20~30 步）
- `fasth3_8step_v2`（蒸馏 8 步版，**站点工作流用的是它**）
- `ref2va_pruned`（多参考图版）

**修法**：训练前确认 LoRA 要挂到哪个底座，就用哪个训。

---

## 14. ai-toolkit 路线在 32GB 内存下会崩

**现象**：加载完 DiT（19.5 GB 反量化）+ 文本编码器（14.6 GB）时，进程直接消失（无 traceback）。

**根因**：两个大模型同时进内存 > 31.8 GB，Windows 直接杀进程。

**修法**：改用 **musubi-tuner 三段式**（缓存 latent → 缓存文本 → 训练），
每段只加载一个模型 + `--blocks_to_swap` 流式换出。

**判据**：`ai-train\runs\*_train.log` 里出现 `Windows 应用日志: 出错应用程序 python.exe`。

## 15. 训练日志要看 `avr_loss` 判断是否在学

| 阶段 | 正常值 |
|---|---|
| 起步 | 2~4 |
| 500 步 | 0.4~0.8 |
| 1000 步 | 0.2~0.4 |
| < 0.1 | 过拟合（学死了素材） |
